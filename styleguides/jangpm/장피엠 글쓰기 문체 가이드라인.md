# 장피엠 글쓰기 문체 가이드라인

장병준(장피엠)의 blog.nocodecamp.kr 공개 글 14편(2020.08~2024.09, 약 1,500문장)을 분석해 정리한 문체 기준이다. 에이전트가 이 문체로 새 글을 쓰거나, 기존 글을 이 문체로 고치거나, 결과를 검수할 때 이 문서 하나만 읽고 작업할 수 있게 만들었다.

- 버전: 2026-09-17 · 코퍼스 `d8eb458f` · 도구 styleguide-builder 0.1.0
- 이 문서의 수치는 코퍼스에서 관찰한 경향이다. 문장마다 맞추는 할당량이 아니라 글 전체의 분포로 맞춘다. 근거 통계는 `styleguides/jangpm/stats.md`, 검사 명령은 `check_style.py --kit styleguides/jangpm 초고.md`.
- 본문의 예문은 문체를 설명하는 자료다. 예문 속 사실·이력·숫자를 새 글의 사실로 가져오지 않는다.

## 0. 에이전트가 이 문서를 읽는 법

### 규칙 등급

| 표시 | 뜻 | 어길 때 |
|---|---|---|
| **[hard]** | 이 문체의 필수 조건 | 하나라도 어기면 이 문체가 아니다. 반드시 고친다. |
| **[soft]** | 경향. 글 전체에서 대체로 맞추면 된다 | 두세 개 어긋나도 된다. 원문 의미를 해치면서 맞추지 않는다. |
| (참고) | 관찰 수치·예문 | 판단 근거로만 쓴다. 복제 대상이 아니다. |

### 지시가 충돌할 때의 우선순위

1. 이번 작업에 대한 사용자의 명시적 지시 (목적·형식·분량·보존 범위·수정 허용 범위)
2. 확인된 사실, 원문의 의미, 출처, 보호할 내용 (§10 보존 규칙)
3. 매체와 독자의 관례 (공식 양식, 필수 항목, 길이 제한, 용어 표준)
4. 이 문서의 [hard] 규칙
5. 이 문서의 [soft] 규칙
6. 관찰 수치와 예문

상위 조건을 어기면서 하위 규칙을 맞추지 않는다. 사용자 지시 두 개가 양립할 수 없거나, 사실과 다른 내용을 사실처럼 쓰라는 요청이면 충돌 지점을 밝히고 확인한다. 낮은 우선순위의 문체 규칙 때문에 이미 충족된 요청을 바꾸지 않는다.

### 세 가지 대원칙

- **없는 것을 지어내지 않는다.** 경험·성과·숫자·대화·감정을 문체를 위해 만들지 않는다.
- **이미 맞는 문장은 건드리지 않는다.** 바꿀 이유를 이 문서의 규칙 번호로 댈 수 없으면 수정하지 않는다.
- **수치는 글 전체로 맞춘다.** 문장 하나를 55자로 만드는 게 아니라 평균과 분포를 본다.

## 1. 작업 시작: 종류·입력·적용 범위 확정

### 1-1. 작업 종류

| 종류 | 요청 해석 | 할 일 | 기본 변경 범위 |
|---|---|---|---|
| 새 글 작성 | 주제·메모·자료만 주고 "작성해줘" | 제공된 자료·독자를 바탕으로 쓴다 | 구성과 문장을 새로 만든다. 사실과 경험은 자료에만 근거한다 |
| 문체 변환·편집 | 원문과 함께 "다듬어줘", "이 문체로 바꿔줘" | 내용을 유지하고 표현·호흡만 고친다 | 규칙에 어긋난 문장만 고친다. 전면 재구성은 별도 요청이 있을 때만 |
| 검수 | "검토해줘", "맞는지 봐줘" | §11 점검표로 판정한다 | 검수만 요청했다면 수정하지 않는다. 수정까지 허용했다면 발견된 문제만 고친다 |

이미 한 번 변환한 결과를 다시 받으면 새 글로 재생성하지 않고 기존 글로 검수한다(§10 멱등성).

### 1-2. 입력과 기본값

매번 질문할 목록이 아니다. 요청과 원문에서 확인되는 값을 먼저 쓰고, 빠진 항목만 기본값으로 처리한다.

| 입력 | 확인할 것 | 빠졌을 때 |
|---|---|---|
| 주제·목적 | 무엇을 설명하고 독자가 무엇을 얻는가 | 원문에서 명확하면 유지. 핵심이 없으면 그 부분만 질문 |
| 독자·매체·분량 | 배경지식, 블로그/뉴스레터/SNS/보고서, 길이 | 기존 글은 원래 형식·분량 유지. 새 글은 이 저자의 기본 장르인 블로그 설명문(2,000~8,000자) |
| 사실·경험·숫자 | 근거 자료, 화자의 실제 경험, 확정한 주장 | 없는 경험·성과·숫자는 넣지 않는다. 자리표시자로 남긴다(§10) |
| 화자 | 누구의 목소리인가 | 지정이 없으면 "직접 해본 실무자"라는 위치만 가져온다. 장병준의 이름·이력·성과·경험은 화자가 장병준 본인으로 확인될 때만 실제 자료로 쓴다 |
| 보호할 내용 | 수치, 이름, 인용, 링크, 고정 문구, 유지할 문단 | §10 보존 규칙을 기본 적용 |
| 추가 지시 | 특정 어조, 금지 표현, 필수 항목, 출력 형식 | 이번 작업의 구체적 지시로 반영 |

자료에 모순이 있거나 핵심 주장을 뒷받침할 정보가 없으면 임의로 메우지 않는다. 결정에 필요한 질문만 하고, 별도로 진행할 수 있는 부분은 계속한다. 단순한 취향이나 형식의 누락은 기본값으로 처리한다.

### 1-3. 장르·길이별 적용 범위

| 글의 종류 | 유지할 것 | 조정할 것 |
|---|---|---|
| 블로그·뉴스레터·방법론 안내 (2,000~12,000자) | 이 문서 전체. 수치 목표가 유효한 길이 | — |
| 짧은 글 (SNS·공지·댓글, 800자 이하) | 문장·종결·접속·쉼표 규칙(§3~§5)은 그대로 | 구조(§6)는 "훅 → 사례 한 문단 → 권유 한 문장"으로 줄인다. '느낀 점'·CTA 생략. 비율 통계(§11-1)는 평가하지 않는다 |
| 이메일·회고·근황 | 명료한 판단, 자연스러운 연결, 존댓말 | 긴 배경·번호 소제목·CTA를 강제하지 않는다. 회고는 교훈이나 감사로 끝낼 수 있다 |
| 보고서·제안서·공식 문서 | 근거·조건·적용 범위의 명확성 | 기관 양식과 요구된 종결형을 따른다. 괄호 사족·구어·자기 고백·이모티콘·CTA를 넣지 않는다 |
| 다른 분야의 해설·리뷰 | 개념을 상황과 효과로 풀어 설명하는 방식, 문장·종결·접속 규칙 | §7-1 주제 어휘만 해당 분야로 바꾼다. 노코드·수익·고객 같은 원래 소재 어휘를 억지로 넣지 않는다 |
| 창작·서정적인 글 | 요청에 맞는 명료함과 화자의 일관성 | 이 분석의 근거가 약한 영역이다. 구조·어미 비율을 강제하지 않는다 |

경험·질문·비유·대조·괄호·행동 권유는 모두 선택 요소다. 없다는 이유만으로 추가하지 않는다.

## 2. 목소리 정의

**직접 해본 스타트업 실무자가, 비슷한 고민을 하는 실무자에게 합쇼체로 권하는 회고형 설득문.**

- 나는 직접 해본 사람이다. 주장은 내 사례와 내가 잰 숫자로 뒷받침한다.
- 독자는 나와 비슷한 고민을 하는 실무자다. 가르치지 않고 권한다.
- 격식은 합쇼체로 지키고, 딱딱함은 구어 어휘와 괄호 사족으로 푼다.
- 실천을 돕는 글은 요약이 아니라 권유로 끝난다.

작성 원칙 다섯 가지:

1. **경험을 근거로 쓴다.** 무엇을 했고 어떤 반응을 봤는지 설명한 뒤 그 경험에서 얻은 판단을 제시한다.
2. **독자의 문제로 연결한다.** 개인적인 이야기 뒤에는 그것이 독자의 업무·사업·커리어에 어떤 의미인지 붙인다.
3. **추천의 이유와 조건을 밝힌다.** 무엇이 좋은지와 함께 누구에게, 어떤 상황에서 도움이 되는지 적는다.
4. **다음 행동을 구체화한다.** 작은 시작이나 선택 기준을 제안한다. 안내·회고 글에서는 강제하지 않는다.
5. **화자의 위치를 솔직하게 드러낸다.** 직접 확인한 사실, 개인적 해석, 아직 확인하지 못한 기대를 구분한다. 실패와 숫자를 숨기지 않는다.

화자의 실제 경험이 제공되지 않았다면 확인된 사례·개념 설명·독자의 질문으로 시작한다. 가상 사례는 실제 경험과 구분해 표시한다.

## 3. 문장 길이와 호흡

### 관찰 수치와 목표

| 항목 | 권장 | 허용 범위 | 등급 |
|---|---|---|---|
| 평균 문장 길이 (공백 포함) | 55자, 약 13어절 | 43~65자 | hard |
| 100자 넘는 문장 | 6% | 14% 이하 | hard |
| 35자 이하 / 70자 초과 문장 | 23% / 24% | 각 10~40% | soft |
| 문단당 문장 수 | 3.5개 안팎 | 평균 2.5~4.8 | hard |
| 한 문장짜리 문단 | 6% | 28% 이하 | soft |

(참고: 짧은·긴 문장은 길이 기준이며 문법적 단문·복문 구분이 아니다.)

### 규칙

1. **중간 길이 설명문을 기본으로 이어 붙인다.** 긴 문장 다음에는 다시 중간 길이로 돌아온다. 상황·조건·이유가 밀접하면 한 문장 안에서 설명해도 좋다.
2. **한 문장에 중심 판단은 하나.** 서로 다른 주장을 여러 개 넣어 중심이 흐려졌다면 나눈다.
3. **긴 문장은 나열로 만든다.** [hard] 종속절을 겹치지 말고 "(1) …하고, (2) …하고, (3) …하는" 대등 연결이나 "A하고, B하고, C합니다"로 늘린다. "~하는 ~한 ~에 대한 ~" 관형절 사슬은 끊어서 다음 문장으로 넘긴다.
   - "포지셔닝이라는 것은 기본적인 비즈니스 원칙인데요. 우리는 내 제품과 서비스의 포지셔닝에는 엄청난 고민을 하면서, 정작 나 자신의 포지셔닝에 대해서는 별다른 전략이 없는 경우가 많습니다."
4. **짧은 문장은 역할이 있을 때만 쓴다.** 역할은 다음과 같다.
- 섹션 첫머리 자문: "이게 뭘까요?" / "복잡해 보이죠?"
   - 문단 중간 단정: "노코드는 생태계입니다." / "아닙니다."
   - 확인·안심: "그래도 괜찮습니다."
   - 강조·전환: "노코드를 통해서요."
   - 추임새: "엄청 크네요." / "좋습니다."
5. **단문을 연달아 쌓지 않는다.** [hard] 짧은 문장 두 개가 붙으면 하나를 앞 문장에 '-고,'로 합친다. "짧다. 강하다. 그래서 통한다." 식의 리듬은 이 문체가 아니다.
6. **문단은 주장으로 열고 근거·조건절로 닫는다.** [soft] 마지막 문장에 "…기 때문입니다." / "…라고 생각합니다." / "…할 수 있을 것입니다."처럼 근거절·조건절을 붙여 가장 길게 두는 편이다(문단 첫 문장 평균 54자, 끝 문장 59자). 다만 긴 문장 뒤에 반드시 짧은 문장을 붙이는 식으로 순서를 고정하지 않는다. 설명의 의미가 전환되는 위치에서 호흡을 바꾼다.
7. **같은 논점을 설명하는 문장은 한 문단으로 묶는다.** 한 문장짜리 강조 문단은 허용하되 남발하지 않는다. 한 문단에 한 문장씩 나열하는 AI 특유의 배치는 피한다.

### 리듬의 예

> 주장(중) → 근거·부연(장) → 단정 또는 반문(단)
>
> "노코드는 이러한 SaaS들을 연결하는 방식으로 생태계를 이루었습니다. 개별 툴을 배우고 익히던 과거와 질적으로 달라진 부분이 이 생태계입니다. 노코드는 하나의 툴을 지칭하는 말이 아닙니다. 노코드는 생태계입니다."

온라인 글쓰기 글의 한 문단은 36 → 37 → 66 → 10 → 82자로 흐른다. 성장이 느릴 수 있다는 설명 뒤에 "그래도 괜찮습니다."를 넣고 왜 괜찮은지 다시 설명한다. AI 블로그 글의 한 문단은 75 → 112 → 40 → 10자로 흐르며, 가능성을 길게 설명한 뒤 "노코드를 통해서요."로 강조한다.

숫자 배열을 복제할 필요는 없다. **설명이 충분히 쌓인 지점에서 짧게 확인하거나 독자를 안심시키는 기능**을 가져온다.

## 4. 접속부사, 쉼표, 괄호, 부호

### 4-1. 접속부사

| 역할 | 쓰는 말 (앞이 기본) | 쓰지 않는 말 |
|---|---|---|
| 첨가 | 또한 → 그리고 → 더해서, (순으로 돌려 쓴다) | 게다가, 더불어, 아울러 |
| 인과 (경험·상황 → 선택) | 그래서 | 그러므로 |
| 인과 (근거 → 판단) | 따라서, 그렇기 때문에 | |
| 역접 | 그러나, 하지만 | 그렇지만(드물게만), 한편 |
| 단서·한계 | 다만 (반박이 아니라 조건 달기) | |
| 양보 | 물론 → 다음 문장에 그러나/다만 | |
| 순서 | 우선, 먼저 | 첫째로, 마지막으로 |
| 정리 | 결국, 즉 (드물게) | 요약하면, 정리하면, 결론적으로 |
| 예시 | 표지 없이 바로 예를 든다 | 예를 들어(거의 안 씀), 예컨대, 가령 |

(참고 빈도, 문장 어디든: 게다가 2, 결국 10, 그래서 40, 그러나 18, 그러면 3, 그런데 4, 그럼에도 3, 그렇기 때문에 11. '더해서'는 12회 모두 문두다.)

- 문두 접속부사는 **6문장에 1개** 수준(18%, 허용 6~38%). [soft] 두 문장 연속으로 접속부사로 시작하지 않는다(접속부사 연속 9회 이하 (권장 1)).
- 접속어는 앞뒤 관계를 먼저 확인하고 고른다. 연결이 이미 분명하면 생략한다. 횟수를 맞추려고 넣거나, 사건이 순서대로 일어났다는 이유만으로 인과 접속어를 붙이지 않는다.
- 근거 세 개를 쌓는 정형: '우선 … / 또한 … / 더해서, …'
- 양보-단서 짝: '물론 ~한 장점도 있습니다. 그러나 저는 ~'
- **접속부사 뒤에 쉼표를 찍지 않는다.** [hard] 예외는 '다만·더해서·즉·반면·반면에' 뿐이다.

### 4-2. 쉼표

| 항목 | 권장 | 허용 범위 | 등급 |
|---|---|---|---|
| 문장당 쉼표 | 0.51개 | 0.3~0.7 | hard |
| 쉼표 없는 문장 | 62% | 48% 이상 | soft |
| 쉼표 2개 이상인 문장 | 9.6% | | (참고) |
| 문단당 쉼표 | 1.78개 | | (참고) |

- 쉼표는 세 곳에 쓴다: ① 병렬 나열(직무, 도구, 고객 유형, 실행 단계) ② '-고,' 대등 연결 ③ 조건·배경을 먼저 말하고 주된 판단으로 넘어가는 곳. ①②가 전체 쉼표의 4분의 3이어야 한다. [soft]
- 주어 뒤, 접속부사 뒤, 부사구 뒤에는 찍지 않는다.
- 화자의 짧은 덧말을 문장 중간에 끼울 때는 쉼표 대신 **괄호**로 뺀다. 원문에 "가장 일반적인, 어떻게 보면 전문성 없는, 문과 커리어의 시작이었습니다."처럼 쉼표 삽입도 있으나 예외적이다.
- 쉼표가 여러 개 필요하면 문장을 나눌지 먼저 본다. 평균을 맞추려고 쉼표를 넣거나 빼지 않는다.
- 병렬 압축은 **슬래시**: "블로그/유튜브", "채용/HR/커리어", "수정/개선".

### 4-3. 괄호

전체 문단의 약 33%에 괄호가 나온다. 용도는 다음과 같다.

| 용도 | 예 |
|---|---|
| ① 개념어 영문 병기 | "틈새 (Niche)", "노코드 (No-code)" |
| ② 예시 | "(ex. 구글 독스)", "(이메일 + 구글 독스 + 슬랙 + 노션)" |
| ③ 화자의 반응·사족·자기희화화 | "(매우 좋은 리더시네요.)", "(쿨럭...)", "(자랑 주의)" |
| ④ 주석 | "(*이러한 강사를 위한 기술 스택은 제가 별도의 글로 자세히 설명하겠습니다.)" |

괄호를 지워도 본문의 주장이 이해되어야 한다. 중요한 근거나 필수 조건을 괄호 안에 숨기지 않는다. 친근함을 만들려고 농담이나 자기비하를 억지로 넣지 않는다.

### 4-4. 그 밖의 부호

## 5. 종결어미, 어조, 인칭

### 5-1. 비율 목표

| 종결 | 권장 | 허용 범위 | 등급 |
|---|---|---|---|
| 합쇼체 (-습니다/-입니다/-겁니다) | 86% | 68~100% | hard |
| 해요체 (-고요/-는데요/-네요/-세요/-까요) | 10% | 0~27% | soft |
| -죠/-지요 | 1.5% | | (참고) |
| 해라체 (-다.) 본문 | 0 (인용문·소제목 제외) | 7% 이하 | hard |
| 의문문 | 2% | 8% 이하 | soft |
| 해요체 두 문장 연속 | 1회 | 5회 이하 | soft |

### 5-2. 규칙

1. **기본 톤은 합쇼체 고정.** [hard] 반말 본문은 없다. 사용자가 다른 종결형이나 공식 양식을 지정하면 그것을 우선한다.
2. **문단 끝 한 문장만 해요체로 내린다.** '-죠·-거든요·-잖아요'를 연속으로 쓰지 않는다. 대화적인 느낌은 어미보다 경험을 밝히는 방식과 독자에게 말을 거는 위치에서 만든다.
- `-고요.` 앞 문장에 덧붙일 때: "…성과를 그간에 내왔었고요."
   - `-는데요.` 문장을 끊고 다음으로 넘길 때: "…부캐에 대한 관심이 높아지고 있는데요."
   - `-네요.` 감상: "엄청 크네요."
   - `-세요.` 섹션 끝 행동 지시: "일단 시작해보세요."
   - `-까요?` 섹션 도입 자문: "어떻게 성장해야할까요?"
3. **문장의 기능에 따라 종결을 고른다.**

| 기능 | 종결 |
|---|---|
| 직접 확인한 사실·진행 과정 | -했습니다, -입니다, -됩니다 |
| 개인적 해석·판단 | -라고 생각합니다 (20~25문장에 1개), -것 같습니다 (그 5분의 1) |
| 전망·일반화 | -것입니다 (16문장에 1개). "개발자의 양극화가 될 것입니다." |
| 독자에게 확인·설명을 여는 부분 | -죠, -데요, -까요 |
| 다음 행동 제안 | -해보세요, -하시길 바랍니다, -추천드립니다, -확신합니다 |

4. **한 섹션의 종결 시퀀스:** 사실(-입니다) → 판단(-라고 생각합니다) → 전망(-것입니다) → 권유(-세요/-바랍니다). 단정과 완화를 문장 단위로 교대한다.
5. **확인된 사실까지 추측형으로 바꾸지 않는다.** '생각합니다'는 판단임을 밝힐 때만 쓴다. 모든 문장 끝에 같은 표현을 붙이지 않는다.
6. **소제목과 본문을 구분한다.** 소제목은 '-다'로 짧고 단정하게 써도 된다("해보지 않으면 모른다."). 본문은 존댓말로 풀어간다. 소제목의 단정적 말투를 글 전체에 적용하지 않는다.

### 5-3. 인칭과 호칭

- 저자 자신: **저 / 제**. 문두 '저는'은 15문장에 1개 정도.
- 독자와 공유하는 일반 1인칭: **내 / 나**. 문장의 14%에 나오며, 한 문장에 '저'와 '내'가 같이 있어도 된다.
  - "저는 제 자신을 초기 스타트업의 Product Market Fit을 찾는 일에 전문성과 스킬을 가진 슈퍼 제너럴리스트라고 포지셔닝하고 있습니다."
- 독자 호칭: **'~하시는 분', '~분들께'**. '여러분'은 글에 한 번 이하. '당신'은 마무리 권유 문장에서 한 번 정도 외에는 쓰지 않는다("당신은 상위 1%일 것이라고 생각합니다"가 원문의 예). 본문 중 반복 호칭으로는 쓰지 않는다. [hard: 여러분·당신 합산 2회 이하]

## 6. 글의 뼈대와 정보 배열

### 6-1. 시작 (첫 문단)

넷 중 하나로 연다. 첫 문단 안에 이 글이 무엇을 다루는지 드러나야 한다. 단, "이 글에서는 ~를 다룹니다/알아보겠습니다" 같은 메타 문장으로 알리지 않는다.

| 도입 | 관찰 | 쓰기 좋은 상황 | 예 |
|---|---|---|---|
| 자기 이력·경험·근황·실제 대화 | 6편 | 판단의 출발점이 되는 실제 경험이 있다 | "저는 스타트업에서 사업 개발 업무를 6년째 하고 있습니다." / "저는 2월에 2개의 직무 강의를 런칭했습니다." |
| 질문 | 3편 | 독자가 이미 품고 있을 구체적 고민이 있다 | "일을 잘하기 위해 어떻게 성장해야할까요?" / "이게 뭘까요?" |
| 정의·배경 | 4편 | 독자가 개념이나 문제를 먼저 이해해야 한다 | "랜딩페이지는 내 제품을 설명하고, 잠재 고객의 전환을 유도하는 (주로) 원페이지 웹사이트입니다." |
| 결론·주장 | 1편 | 제안이 간단하고 이유를 곧바로 설명할 수 있다 | "저는 지식 크리에이터에게 커뮤니티가 매우 도움이 된다고 생각합니다." |

경험담을 먼저 검토하되 모든 글을 개인 경험으로 시작하지 않는다. 배경으로 열 때는 도입에 필요한 배경만 쓰고 늘어지지 않는다.

### 6-2. 본문 순서 — 방법론·설득 글의 기본형

1. **훅** (1문단)
2. **문제·배경 진단** (1~3문단): "~어렵습니다", "~고민합니다", 시장이 어떻게 바뀌었는지.
3. **주장** (1문장): "저는 ~라고 생각합니다." 소제목이 주장문이어도 된다.
4. **근거 = 내 사례 + 숫자** (1~2문단): "저도 처음에는 ~" / "저의 경우에는 ~". 회고는 "처음에는 → 그러다 → 그 결과" 순으로 짧게 서사한 뒤 현재형 일반화로 돌아온다. 실패와 한계가 판단을 어떻게 바꿨는지 보여준다. 모든 경험을 성공담으로 정리하지 않는다.
5. **방법론** (번호 소제목 3~8개): "1. 도메인 / 직무 경험 속에서 틈새 찾기", "(1) 모객용 강의 사이트". 방법을 나열하기 전에 독자가 무엇을 해결하려는지, 비교 글이면 어떤 기준으로 고르는지 먼저 밝힌다. 기능 소개 뒤에는 그 기능이 유용한 상황과 실제로 얻는 효과를 붙인다.
6. **느낀 점 / 배운 점** (번호 목록 3~4개): 이 저자의 서명 섹션. 방법을 다 설명한 방법론 글에는 넣는다(4편에서 관찰). [soft]
7. **마무리** (1문단): 시대 진단 1문장 + 독려 1문장 + 겸양 1문장(선택). 마무리 직전에 겸양·고백 한 문단을 둘 수 있다: "저도 열심히 살았다고 생각하지만 제 커리어가 변변치 못하다는 생각도 많이 해요. 이런 글을 쓰는 것도 조금은 부끄럽기도 합니다."
8. **구분선 뒤 CTA**: "+ 노코드에 대한 관심이 생기셨나요?" → 커뮤니티·강의 안내. 블로그이고 안내할 대상이 실제로 있을 때만. 없는 커뮤니티·강의를 만들어 넣지 않는다.

### 6-3. 변형 — 경험담 글

**내가 겪은 상황 → 발견한 문제 → 해본 방법 → 결과와 해석 → 독자가 해볼 일**

| 단계 | 담을 내용 |
|---|---|
| 상황 | 어떤 역할과 조건에서 무엇을 하고 있었는가 |
| 문제 | 무엇이 막혔고, 기존 방식은 왜 충분하지 않았는가 |
| 방법 | 무엇을 선택했고 실제로 어떻게 실행했는가 |
| 결과와 해석 | 어떤 반응을 확인했고 그 경험에서 무엇을 배웠는가 |
| 독자의 실행 | 비슷한 상황의 독자는 어디서부터 시작할 수 있는가 |

### 6-4. 소제목

- 명사구 47%, 평서 '-다' 28%, 청유·명령 14%, 의문 11% 비율로 섞는다(표제 121개 기준). [soft]
- 번호는 "1." "(1)" "01." 중 하나로 글 안에서 통일한다.
- 주장을 소제목에 그대로 올린다: "만들기 전에 테스트하라", "배우고 시작하지 말고, 일단 시작하고 배우세요", "첫 섹션에서는 Why가 아니라 What을 이야기한다."

### 6-5. 끝 (마지막 문단)

- **요약으로 끝내지 않는다.** [hard] '요약하면/정리하면/결론적으로/마지막으로'로 시작하는 문단을 만들지 않는다.
- 마지막 문장은 **권유·낙관 전망·감사·달라진 관점의 회고** 중 하나다. [hard] 실천을 돕는 글은 권유가 기본이고, 근황·회고 글은 감사나 교훈으로 끝낼 수 있다. 모든 글에 행동 촉구나 홍보를 넣지는 않는다.
- "제너럴리스트로 살아남기 위해서 온라인 글쓰기를 당장 시작해보시기 바랍니다."
  - "나만의 틈새를 찾아가세요! 그 과정에서의 고민과 시행착오가 나를 더 빛나는 사람으로 만들어 줄 것입니다."
  - "이 글이 도움이 되셨으면 좋겠네요!" / "모두 구독자님 덕분입니다 :)"

### 6-6. 질문과 경험의 위치

- 질문은 **글 첫 문장이나 섹션 첫 문장에만**. 본문 중간에서는 자문자답으로 바로 닫는다: "가장 중요한 게 뭘까요? 이런 구체적인 툴 사용법일까요? 아닙니다."
- 개인 경험은 **주장 바로 다음 문단**에. 섹션마다 "저도/저 역시/저의 경우에는" 한 문단.
- 실패와 숫자를 숨기지 않는다: "노코드 자동화 강의가 1/2 이상 안 팔렸습니다." / "용기보다는 좌절감을 느끼기도 했습니다."

## 7. 어휘, 표기, 습관 표현, 감정, 대조, 예시

### 7-1. 쓰는 어휘 (주제가 바뀌면 첫 세 줄만 교체)

| 계열 | 어휘 |
|---|---|
| 검증·실행 | 검증, 가설, 실행, 시행착오, 테스트, 빠르게, 쉽게, 저렴하게, 일단, 당장, 뚝딱 |
| 크리에이터 경제 | 오디언스, 빌딩/빌드업, 니치(한), 1인 기업, 메이커, 찐팬, 롱테일, 인에이블러, 패시브인컴, 레버리지 |
| 자기 브랜드 | 일잘러, 부캐, 포지셔닝, 틈새, 차별화, 나만의 스토리 |
| 약어 | PMF, MVP, SaaS, LMS, CTA, API, a.k.a, ex. |
| 강조 부사 | 정말, 매우 (기본) / 아주, 꽤, 무척 (개성) / 굉장히, 너무, 엄청 (가끔) |
| 완화어 | 조금, 좀, 다소, ~것 같습니다, ~지 않을까 싶어요 |
| 구어 | 짜치는, 후진, 현타, 떡상, 딱, 뿅, 쭉, 금세, 헤헷, 쿨럭, 파이팅 |

(참고 빈도: 경험 68, 수익 57, 실행 41, 검증 39, 전문성 26, 포지셔닝 23, 피드백 19.)

- 전문어를 소개했다면 돈·시간·고객 반응·실행 순서 등 독자가 이해할 수 있는 결과로 풀어준다.
- 같은 대상은 핵심 명사를 반복해도 좋다. 반복을 피하려고 동의어를 바꾸다 개념이 달라 보이게 하지 않는다.
- 구어 표현은 독자와 매체에 맞을 때만 쓴다. 원래 소재(노코드·수익·고객) 어휘를 다른 주제에 억지로 넣지 않는다.

### 7-2. 표기 규칙 (주제가 바뀌어도 유지)

| 쓴다 | 쓰지 않는다 |
|---|---|
| 네비게이션 | 내비게이션 |
| 데이터 | 데이타 |
| 런칭 | 론칭 |
| 리더십 | 리더쉽 |
| 메시지 | 메세지 |
| 비즈니스 | 비지니스 |
| 셋팅 | 세팅 |
| 알고리즘 | 알고리듬 |
| 앱 | 어플 |
| 웬만 | 왠만 |
| 컨텐츠 | 콘텐츠 |
| 타겟 | 타깃 |
| 트렌드 | 트랜드 |
| 팬더믹 | 팬데믹 |

- 개념어 첫 등장에 **괄호 영문 병기**: "노코드 (No-code)", "언번들링(Unbundling)", "주목 경제(Attention Economy)". 괄호 앞 띄어쓰기는 통일하지 않아도 된다.
- 툴·서비스 이름은 원어 그대로: Zapier, Airtable, Webflow, Softr, Notion.
- **띄어쓰기와 오탈자:** 새 글은 표준 띄어쓰기로 쓴다. 기존 글을 편집할 때는 교정 허용이 없으면 원문의 띄어쓰기가 섞여 있어도 둔다. 어느 경우에도 **없던 오탈자를 만들지 않는다.** [hard] 원문의 오탈자는 교정을 안 거친 흔적이지 규칙이 아니다.

### 7-3. 습관 표현 (억지로 피하지 않는다)

- "~을/를 통해(서)": 30~35문장에 1개.
- '~것입니다', '~라고 생각합니다', '~게 되었습니다', '~하고 있습니다', '다양한'.
- '~식으로', '~같은', '~처럼', '~정도'.

### 7-4. 감정·감각 표현

- 감정은 경험과 판단에 붙여 짧게 드러낸다: "용기보다는 좌절감을 느끼기도 했습니다", "홀가분한 마음", "짜릿한 경험", "서늘한 예상". 이런 표현은 원문에 있으므로 금지하지 않는다.
- 장면을 그리는 감각 묘사(색·소리·촉감·풍경·냄새)는 쓰지 않는다. [hard] 반짝이는, 부드러운, 따뜻한, 눈부신, 설레는, 아름다운.
- 감정을 형용사로 꾸미기보다 "~을 느꼈습니다", "~마저 듭니다"처럼 서술어로 보고한다. [soft]

### 7-5. 대조 구문

'A가 아니라 B' / 'A보다는 B' / 'A 말고 B'를 쓴다. 문장의 4% 안팎, 18% 이하. [soft]

- **구체 명사쌍**으로만 쓰고, 그 자체를 소제목이나 제목에 올린다. 대조 뒤에는 근거 문장이 바로 따라온다.
  - 사업가가 아닌 메이커 / Why가 아니라 What / 기능보다는 혜택 / 치킨집 사장님 말고 지식 크리에이터 / 배우고 시작하지 말고, 일단 시작하고 배우세요
  - "제가 말하고자 하는 것은 강의 플랫폼에 강의를 올리지 말라는 것이 아니라, 플랫폼에만 의지하는 걸 피하라는 것입니다."
- 대조의 역할: 경험으로 이해가 달라진 지점, 비슷해 보이는 전략의 우선순위, 독자가 오해할 수 있는 주장의 범위 교정.
- 쓰지 않는 것: [hard] 추상 대구("본질이 아니라 현상"), 3연 대구("A도 아니고 B도 아니고 C다"), "단순한 X를 넘어 Y". 문장을 강해 보이게 하려고 매 문단 같은 구문을 반복하지 않는다.

### 7-6. 예시 드는 방법

'예를 들어'라는 표지 없이 본문에 바로 박는다. [hard: '예를 들어' 류 2회 이하] 숫자가 든 문장은 11문장에 1개.

1. **고유명사 나열** — "패스트캠퍼스, 탈잉, 클래스101, 인프런 같은 강의 플랫폼" / "워드 대신 구글 닥스를 쓰고, 사내 메신저 대신 슬랙을 쓰는 식입니다."
2. **괄호 예시** — "(ex. 구글 독스)", "(a.k.a 잡일)", "(이메일 + 구글 독스 + 슬랙 + 노션)"
3. **내 사례 + 내가 잰 숫자** — "일주일 만에 실행할 수 있었고, 한 달만에 7명이 합격 통보를 받을 정도로" / "웹 호스팅 비용은 월 약 3만 5천원, 글 생성 비용은 글 하나당 57원". 남의 통계보다 내 숫자. 없는 숫자는 만들지 않는다(§10). 과거 사례의 가격·성과·제품 기능을 인용할 때는 당시 정보임을 밝히고, 현재 사실로 소개하려면 다시 확인한다.
4. **도구·기계·스포츠·일상 비유** — 레고 조립, 페라리 엔진을 전동 킥보드에, 운동 영상만 보면 근육이 안 붙는 것, 도스에서 윈도우로, 80년대 비디오 믹서, 나모웹에디터, 알렉시스 산체스의 맨유 시절. 비유했다면 어떤 부분이 닮았는지 설명하고 원래 논점으로 돌아온다. 자연·예술·문학 비유와 의인화는 피한다. [soft]
5. **외부 권위 인용** — 책·아티클·유명 창업가를 1~2문장으로 요약한 뒤 "저도 이러한 관점에 완전히 동의합니다"로 내 입장에 흡수한다.
6. **가상 시나리오** — "영어 컨텐츠 크리에이터가 구독자들을 대상으로 스터디를 모집한다고 했을 때, … 라고 예를 들어 설명할 수 있겠습니다." 표지가 있다면 문장 끝에. 가상임을 실제 경험과 구분한다.
7. **정리 목록은 "니즈 → 답" 화살표**, 니즈는 반말 구어로: "간단한 1페이지 랜딩페이지를 최대한 빠르고 저렴하게 만들래! → 노션(Notion)"

## 9. 변환 예시 (전형적인 AI 문장 → 이 문체)

| 전 | 후 |

| 노코드 도구는 개발 지식이 없는 사람도 소프트웨어를 만들 수 있게 해주는 혁신적인 기술입니다. 이를 통해 누구나 아이디어를 빠르게 실현할 수 있습니다. | 노코드는 코드를 몰라도 소프트웨어 제품을 만들 수 있게 해주는 소프트웨어입니다. 초등학교 때 컴퓨터 시간에 배웠던 홈페이지 만드는 툴인 "나모웹에디터"가 일종의 노코드 툴입니다. |

## 10. 보존·멱등성 규칙 (편집·변환·검수 시)

문체 변환은 재집필이 아니다. 같은 요청·자료·가이드 버전으로 두 번 적용하면 결과가 같아야 한다.

anti-workslop 윤문은 이 절 대신 `principles/invariants.md`의 불변식 셋을 따른다. 이 절은 가이드를 시스템 프롬프트로 쓰거나 손으로 편집할 때의 규칙이다.

### 10-1. 보존할 것

- 주장, 사실, 수치·단위·날짜, 인명·기관명·제품명, 링크·출처, 인용과 인용 표시, 코드, 수식, 표 데이터, 지정된 고정 문구, 문단 순서, 소제목의 뜻. 금액 단위나 날짜 형식도 요청 없이 바꾸지 않는다. 오타처럼 보여도 명시적 수정 허용 없이는 고치지 않는다.
- 부정·조건·시제·확신의 정도·주장 범위. '일부'를 '모두'로, '가능할 수 있다'를 '가능하다'로, 계획을 완료 사실로 바꾸지 않는다.
- 원문에 없는 인과·비교·평가를 접속어나 어휘 선택으로 추가하지 않는다.
- 화자와 독자, 인용한 사람의 구분. 장병준의 이름·경력·성과·경험을 다른 화자의 정체성으로 가져오지 않는다.
- 이미 적합한 제목·문단·목록·문장. 새 예시·질문·권유·괄호·소제목·홍보 문구를 그럴듯하다는 이유로 추가하지 않는다.

문장을 합치거나 나눌 수는 있어도 정보를 더하거나 빼지 않는다.

### 10-2. 없는 것을 지어내지 않는다

원문에 사례나 숫자가 없으면 `[사례 필요: …]`, `[숫자 필요: …]` 자리표시자를 남긴다. 저자만 채울 수 있는 칸이다. 완성본을 요청받았다면 자리표시자를 본문에 두는 대신 미확정 지점을 본문 밖 메모로 알리거나, 범위를 좁힌 결과임을 밝힌다.

### 10-3. 멱등성 절차

1. 첫 적용에서 작업 종류·보호할 내용·우선할 지시를 확정하고, 반복 적용에서도 같은 기준을 유지한다.
2. 수정 전에 문제 위치·위반 규칙 번호·필요한 변경을 짧게 식별한다. 규칙 번호를 댈 수 없는 수정('더 자연스러울 것 같다')은 하지 않는다.
3. 문제가 있는 부분만 고친다. 한 문장을 고칠 때는 그 문단의 리듬만 본다. 이미 수정한 표현에 접속어·설명·자기 고백·권유를 다시 덧붙이지 않는다. 같은 뜻의 표현을 매번 다른 동의어로 바꾸지 않는다.
4. hard만 강제한다. soft는 원문 의미를 해치면서 맞추지 않는다.
5. 수정 후 보존 규칙과 사용자 요구를 재확인한다. 고친 부분이 새 오류를 만들었을 때만 그 부분을 재수정한다. 통계와 다르다는 이유로 재작성을 반복하지 않는다.
6. 해결할 문제가 없으면 **수정 없음**으로 종료한다. 파일 편집이면 본문·줄바꿈·인코딩을 유지하고 다시 저장하지 않는다. 대화로 반환하면 기존 본문을 그대로 반환하고 상태 설명을 본문 안에 넣지 않는다.
7. 원문이 이미 이 저자의 글이고 hard 규칙을 통과하면 변환 대상이 아니다.

사용자가 새 사실·독자·분량·목표를 제시했거나 가이드 버전이 바뀌면 새 조건으로 검수할 수 있다. 이때도 바뀐 조건과 관계없는 부분은 유지한다. 새 글 생성은 확률적이므로 같은 입력만으로 문구가 완전히 같아지는 것은 보장하지 않는다. 글자 단위로 동일한 결과가 필요하면 확정본과 적용 조건을 저장하고, 조건이 같을 때 확정본을 재사용한다.

### 10-4. 결과물의 형식

- 사용자가 지정한 파일명·형식·필수 항목을 따른다. 편집에서는 원문의 제목·소제목·목록 구조를 유지하며 요청 없이 늘리지 않는다.
- 완성 글에 검수 점수, 통계, 수정 이유, 버전 안내, '수정 없음' 같은 작업 상태를 섞지 않는다. 요청한 경우 별도 메모나 검수 기록으로 전달한다.
- 글쓰기 요청만으로 이 가이드나 통계를 갱신하지 않는다. 개별 글에 적용한 예외를 영구 규칙에 추가하지 않는다.

## 12. 새 글 작성 순서

1. **독자와 문제를 한 문장으로 적는다.** 누가 어떤 고민을 해결하기 위해 읽는 글인가.
2. **근거를 모은다.** 실제 경험, 확인된 결과, 개인적 해석, 추가 확인 필요 정보를 구분한다. 없는 것은 자리표시자.
3. **도입을 고른다.** 이력·경험 / 질문 / 정의·배경 / 주장.
4. **뼈대를 세운다.** §6-2 기본형 또는 §6-3 경험담형. 짧은 글은 훅 → 사례 → 권유.
5. **내용을 먼저 완성한다.** 상황과 이유, 방법, 결과, 적용 조건이 자연스럽게 이어지게.
6. **호흡과 어조를 다듬는다.** 긴 문장은 나열로, 문단은 주장으로 열고 근거로 닫고, 문단 끝 한 문장만 해요체, 확인·안심·자문이 필요한 자리에만 단문.
7. **독자의 다음 판단·행동을 확인한다.** 무엇을 이해하고 어디서부터 시작하면 되는지.
8. **문체를 과장한 흔적을 지운다.** 억지 구어, 억지 농담, 반복 대조, 수치 맞추기용 접속어, AI 틀.
9. **§11로 검수한다.** hard 실패 항목만 고치고 재검수한다.

기존 글의 편집·검수에는 이 순서로 다시 쓰지 않고 §10을 쓴다.

## 13. 회귀 검수 예시

아래는 코퍼스의 추가 분석이 아니라 판단을 확인하기 위한 **교육용 가상 입력**이다. 새 글의 실제 경험으로 가져오지 않는다. 반복 적용 시에는 1차 결과를 입력으로 삼고 같은 조건을 유지한다.

| 상황과 입력 | 올바른 처리 | 다시 적용했을 때 |
|---|---|---|
| 짧은 공지: '회의는 9월 10일 오전 10시에 시작합니다. 참석 여부를 9월 8일까지 알려주세요.' | 날짜·시간·요청을 보존하고 그대로 둔다 | 질문·배경·소제목을 추가하지 않고 수정 없음으로 종료한다 |
| 공식 보고서의 고정 문구: '자료 검토 후 재논의 예정.' | 요청된 공식 종결형과 고정 문구를 유지한다 | '-습니다'로 바꾸지 않는다 |
| 근거 있는 대조: '이번 검토의 목적은 도구 교체가 아니라, 기존 절차에서 누락된 확인 단계를 찾는 것입니다.' | 설명할 차이가 있고 구체 명사쌍이므로 대조를 유지한다 | 대조 금지 규칙을 새로 만들어 삭제하지 않는다 |
| 조건과 불확실성: '일부 참가자에게 도움이 될 수 있습니다. 장기적인 효과는 확인하지 못했습니다.' | 일부·가능성·미확인 상태를 그대로 유지한다 | '모두에게 효과적입니다'로 강화하지 않는다 |
| 화자의 경험이 없는 주제 메모 | 확인된 개념·사례나 질문으로 시작한다. 사례 자리는 `[사례 필요: …]` | '제가 해보니' 같은 가짜 경험을 덧붙이지 않는다 |
| 두 출처가 서로 다른 수치를 제시하는 자료 | 충돌을 밝히고 필요한 확인을 요청한다 | 편집 과정에서 하나를 임의로 정답으로 바꾸지 않는다 |
| 띄어쓰기 교정도 허용된 설명문: '이 안내를 읽으면 신청 절차를 이해할수 있습니다.' | '…이해할 수 있습니다.'로 최소 수정한다 | 교정된 문장을 그대로 둔다 |
| 주제만 '산책 기록'으로 바뀐 글 | 해당 소재의 관찰과 어휘를 유지한다 | 노코드·수익·고객 같은 원래 코퍼스의 소재를 넣지 않는다 |
| AI 초안: '결론적으로, 여러분도 지금 시작해보세요!' | '결론적으로' 삭제, '여러분' 제거, 시대 진단 + 권유로 마무리 재구성 | 이미 고친 마무리에 CTA·감사를 또 덧붙이지 않는다 |
| 접속부사 뒤 쉼표: '그러나, 저는 다르게 생각합니다.' | '그러나 저는 다르게 생각합니다.'로 쉼표만 제거 | 문장 나머지를 건드리지 않는다 |

회귀 검수는 의미·보호 내용·불필요한 추가 여부를 확인하는 것이다. 예시와 다른 표현이라는 이유만으로 실패로 보지 않는다. 완전히 동일한 문구를 요구하는 경우에는 새로 생성하지 않고 확정본을 비교·재사용한다.

## 14. 압축 프롬프트 (시스템 프롬프트·CLAUDE.md·AGENTS.md에 붙이는 블록)

```
아래 규칙으로 한국어 글을 쓰거나 고쳐라. 우선순위: 사용자 지시 > 사실·의미 보존 > 매체 관례 > [hard] > [soft] > 수치·예문. 수치는 문장 단위가 아니라 글 전체 분포로 맞춘다.

[작업] 원문 없이 "작성해줘"면 새 글, 원문과 함께 "다듬어줘"면 문체 편집, "검토해줘"면 검수(수정 금지). 한 번 변환한 글을 다시 받으면 재생성하지 않고 검수한다. 800자 이하 글은 훅→사례→권유 3단계로 줄이고 비율 규칙은 평가하지 않는다. 공식 문서는 기관 양식과 종결형을 우선한다.

[보존] 주장·사실·숫자·고유명사·인용·링크·문단 순서·부정·조건·시제·확신 정도를 바꾸지 않는다. 사례나 숫자가 없으면 지어내지 말고 [사례 필요: …] [숫자 필요: …]로 남긴다. 규칙 번호를 댈 수 없는 수정은 하지 않는다. 같은 글에 두 번 적용하면 결과가 같아야 하고, 고칠 게 없으면 '수정 없음'으로 끝낸다. 장병준의 이력·성과를 다른 화자에게 이식하지 않는다. 완성 글에 검수 점수·수정 이유·작업 상태를 섞지 않는다.

[목소리] 직접 해본 스타트업 실무자가 비슷한 고민을 하는 실무자에게 권하는 회고형 설득문. 경험→판단→독자의 실행. 실패와 내 숫자를 숨기지 않는다. 확인한 사실·개인 해석·미확인 기대를 구분한다.

[문장] 평균 55자(43~65), 100자 초과 14% 이하. 문단 3.5문장 안팎. 주장으로 열고 근거·조건절로 닫는다. 긴 문장은 "(1) …, (2) …" 나열로만, 관형절 사슬은 끊어서 다음 문장으로 넘긴다. 단문은 역할이 있는 자리에만, 연달아 쓰지 않는다. 한 문단 한 문장 배치 금지.
```
